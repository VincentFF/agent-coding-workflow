# 工作流说明

## 一次交付的完整路径

```text
讨论
  └─ change-planning          # 组织交付：目标、边界、材料、任务、验收
       ├─ prd-writing         # 需要澄清产品目标/范围/规则时
       ├─ design-writing      # 需要技术结构时（内部按需调用领域建模、代码结构设计）
       └─ spec-writing        # 需要精确定义行为时
            ↓ 列出材料集合，取得批准
  └─ agent-workflow           # 执行已批准交付
       ├─ implementer + tdd
       ├─ code-reviewer        # 独立评审，不继承实现上下文
       ├─ 文档合并              # 目标 Spec → 当前 Spec 等
       └─ 最终验证与归档
```

各技能由 `change-planning` 与 `agent-workflow` 协调。技能之间不自动互相派发，避免循环调用。

## 四种文档的角色

| 文档 | 回答的问题 | 状态 |
| --- | --- | --- |
| PRD | 为谁解决什么问题，产品应提供什么，如何判断有价值 | 可包含未交付需求 |
| Spec | 系统在给定输入下产生什么结果、保留什么状态 | 当前 Spec 表示已交付；Change 内的 Spec 表示本次目标 |
| Design | 用什么结构和机制实现 | 区分当前结构与目标架构 |
| Change | 这次交付什么、怎么推进、怎么验收 | 有 draft / approved / accepted 状态 |

**需求已确认、能力已实现、效果已验证是三个不同事实。** 文档不能把它们混写成一句"已支持"。

## 交付目录

新交付使用目录：

```text
docs/changes/YYYY-MM-DD-<topic>/
  change.md     # 交付入口：目标、材料、任务、验收、合并、结论
  spec.md       # 目标行为契约（有行为变化时）
  prd.md        # 可选：产品要求
  design.md     # 可选：实质技术设计
```

不为凑齐而创建空文件。小范围技术选择可留在 `change.md`。

## 为什么单独评审

实现者会倾向于相信自己完成的工作。独立评审的价值在于：

- 用原始契约而不是实现者的描述判断行为。
- 检查测试是否真的验证了目标，而不是复制实现逻辑。
- 发现"看起来通过"但不能证明真实边界（事务、进程、网络）的证据缺口。

因此评审者需要固定的比较基线、完整变更范围和不继承实现对话的上下文。是否真正独立取决于宿主能力，项目接入文件应如实记录实际具备哪一种。

## 目标 Spec 如何进入当前 Spec

1. 规划时编写目标 Spec，只覆盖受影响能力。
2. 批准后它是实施与验收依据，但**不代表已交付**。
3. 实现并验证后，把已交付部分语义合并进最新应用 Spec：替换受影响章节，保留其他有效保证。
4. 其他 Change 期间改过同一区域时，先核对再合并，不覆盖更新的保证。
5. 归档中的目标 Spec 作为历史依据保留，不再跟随演化。

不回写"直接追加"或"整份覆盖"，也不允许只完成部分范围就按整体验收。

## 简化原则

工作流本身刻意不使用脚本校验文档语义。链接、格式、关键词或章节数量都不能证明：

- 契约是否完整。
- 测试是否证明了承诺。
- 评审是否独立发生。

这些只能通过阅读原始材料和真实运行来确认。可选的候选身份工具（`candidate.py`）只帮助确认"验证结果对应哪份源码"，不判断正确性。

## 专项方法与按需加载

随着工作流涵盖 Go、PostgreSQL、错误处理及 LLM 成本/缓存等专业领域，工作流引入了**任务级专项方法**：

- 导航入口：`skills/agent-workflow/references/task-methods.md`。
- 按需加载：不一次性把所有专项技能加载到上下文；只有遇到对应语言（如 Go）、技术边界（如 SQL/Migration）或具体疑问（如 LLM 费用）时才读取对应规则。
- 角色不膨胀：专项规程（如 `go-review`、`silent-failures`、`postgres-review`、`output-evaluation`、`go-build-recovery`）是现有角色（`implementer`、`code-reviewer`、`oracle`）的工作方法与审查视角，不新增 agent 角色。
- 契约优先：通用专项技能中的建议不能覆盖目标项目既有的部署策略、迁移工具或接口契约。
