# 采用与定制

## 采用一个项目

1. 把仓库地址和目标版本交给 AI，要求按 `INSTALL.md` 安装。
2. AI 调查项目现有规则、文档位置和验证入口，向你确认无法判断的部分。
3. 它分发技能、接入运行环境、生成 `.agents/project-workflow.md`、在入口文件合并受控区块。
4. 它报告实际改动与无法确认项。

首次采用后，先跑一个真实的小变更验证流程，不要直接用于大规模改造。

## 定制边界

定制分三类，处理方式不同：

| 想改的内容 | 应该改哪里 |
| --- | --- |
| 通用方法本身有问题（步骤、完成条件、调用关系） | 上游仓库；本地改动会在升级时冲突 |
| 项目约定（文档位置、验证命令、授权规则） | `.agents/project-workflow.md` |
| 项目额外规则（额外审查、特殊发布流程） | 项目自己的 `AGENTS.md` 区块外，或 `project-workflow.md` 的"项目专属约束" |

不要为了适配某个项目去修改技能正文。分发副本被改动后，升级会需要人工比较，且容易长期偏离上游。

## 升级

升级时 AI 会比较"旧版本、当前文件、新版本"：

- 未改动的受管文件直接更新。
- 有本地改动的文件保留定制并应用新变化，实质冲突时报告。
- 项目接入文件默认保留，只补新增的通用要求。
- 入口区块原位更新。

不要用强制覆盖或删除整个 `.agents/` 来"重装"。

## 不纳入工作流项目的内容

以下内容按项目自身需要决定，不属于通用工作流：

- 具体模型或供应商选择。
- 项目特有的测试框架和门禁。
- 业务领域术语。
- 部署与发布流程。
- 内部合规或审计要求。

通用工作流只约束**方法与职责边界**，不替项目规定技术选型和业务规则。

## 多语言与多环境

技能用英文写作以保持跨项目一致；项目自己的文档语言由 `project-workflow.md` 与项目原有习惯决定。工作流不要求把项目文档翻译成英文，也不要求在通用技能中混入项目语言。

同一项目可同时接入多个运行环境。角色模板按环境分别维护，但都引用同一份 `.agents/skills/`，不复制技能内容。

## 专项技能与项目技术栈

通用技能中包含 Go、PostgreSQL、数据库迁移等专项方法，但**通用技能不锁定项目具体工具**：

- 项目使用 Atlas、goose、golang-migrate 或 Flyway，写在 `project-workflow.md` 中，技能遵循项目实际契约。
- 项目使用特定的 LLM 供应商或 SDK，配置与代码归项目所有，通用技能提供 token 计量、预算与缓存比较方法。
- 不需要某项技术栈的项目（例如纯 Python 或前端项目），在任务匹配时自然不会加载对应专项技能（如 `golang-patterns`）。
